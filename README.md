# laim-traces-dataset-converter

Нода LAIM извлекает пары «внешний запрос — ответ агента» из AEF-спанов и
публикует monitoring UMR. Формат UMR задаёт `monitoring_metric.assessment_mode`:
он совпадает с форматом reference UMR, выбранным `laim-baskets-adapter`.
Нода выполняется в контуре Sber DS. По умолчанию извлечение не использует
LLM и сеть. Необязательный теневой анализ предлагает выбор полей, но не
изменяет публикуемый UMR.

## Входы и выходы

| Вход | Содержимое |
|---|---|
| `monitoring_traces` | DataFrame, байты parquet/XLSX, путь к файлу или каталогу частей |
| `monitoring_metric` | `laim-monitoring-metric.v2`: статус, режим оценки и источники scoring |
| `traces_validation_result` | Вердикт проверки трейсов: schema, quality, criteria K1–K8, readiness, metrics |
| `selection` | Необязательные `agent_ci`, `distributive`, `solution_version` |

Без `selection.agent_ci` входная таблица должна содержать одного агента. Строки
других агентов и строки с пустым `agent_id` учитываются отдельно.

Настройки: `ignore_traces_checks=False`, `min_extraction_coverage=0.9`.
Первая отключает DQ-гейт и оставляет в отчёте `bypassed_dq`. Вторая определяет
минимальное покрытие для `data_readiness`; пропущенные обращения не позволяют
получить статус `complete`.

DQ-гейт использует критерии K1–K6 и итог `quality.valid`. K7 и K8 сохраняются
в `traces_validation.non_gating_criteria` как диагностика. Для K8 допускается
также `tone=muted` — умеренные замечания по структуре телеметрии.

| Выход | Содержимое |
|---|---|
| `monitoring_umr` | DataFrame в формате `laim-umr.v2` |
| `processing_report` | `laim-monitoring-trace-converter.v2`: полнота, причины пропусков, готовность данных |
| `parquet_test_dataset` | Байты parquet с тем же DataFrame |
| `umr_artifact` | `pd.ExcelFile` с одним листом UMR |
| `settings` | Параметры платформенного file-writer; сама нода не пишет в HDFS |

Обязательные колонки спанов: `agent_id`, `trace_id`, `span_id`, `session_id`,
`start_time_ns`, `aef_kind`, `input_text`, `output_text`. `parent_span_id`
нужен для восстановления вложенности. Без него остаётся приоритет граничных
видов спана внутри trace. `span_name` не участвует в выборе ответа.

Поддержаны альтернативные имена колонок AEF: `traceid`, `spanid`, `parentspanid`,
`starttimeunixnano`, `endtimeunixnano`, `name`. Одновременные несовместимые
значения старой и новой колонки — ошибка входа. Время принимается в целых
наносекундах или как pandas Timestamp; отсутствующее время не заменяется нулём.

## Правила извлечения

Извлечение состоит из выбора внешней границы, проекции тела в текст и,
для асинхронного обмена, соединения сообщений по ключу FIPA.
Имена CI, имена узлов LangGraph и поля состояния конкретных агентов
в правилах не используются.

**Граница.** Кандидаты — `input_request`, `kafka_consume`, `start_agent` и
спаны с FIPA-конвертами. Связи родителей разрешаются по `(trace_id, span_id)`.
Вложенный `start_agent` не становится отдельным обращением. Среди корней
одного trace приоритет имеют `input_request`, затем `kafka_consume`, затем
`start_agent`. Несколько внешних спанов одного уровня сохраняются как
отдельные обращения, даже если тексты совпадают.
Для синхронного `start_agent` требуется колонка `parent_span_id` с явно пустым
значением: отсутствующая внешняя граница не превращает внутренний запуск
агента в пользовательский turn.

Совпадающие копии одного спана схлопываются. Конфликтующие копии исключаются;
их потомки не становятся внешними границами. Так же обрабатываются циклы
родителей и неоднозначные конверты предка. Внутренний FIPA-спан может
дополнить внешнее обращение только при совпадении протокольного ключа.

Если у внешнего спана нет входного тела, запрос можно взять у единственного
ближайшего граничного потомка той же сессии. Ответ всегда берётся с внешней
границы. В provenance сохраняется путь `descendant:<span_id>:input_text...`.
Несколько подходящих потомков не разрешаются выбором по времени или длине.

**Текст.** Поддержаны JSON, повторно закодированные объекты и массивы, а также
безопасный разбор Python repr. Проекция использует следующий порядок:

1. Содержимое транспортного конверта. В `content.message` объединяются все
   части `type=text`; виджеты пропускаются, даже если их `value` — строка.
2. Явные сообщения с ролью в `role`, `type`, `speaker` или `speaker_type`.
   Для запроса берётся последняя реплика user/human/customer/client,
   для ответа — assistant/ai/agent/bot после последнего пользовательского
   сообщения. System, tool, function, operator и robot не становятся ответом
   агента. Пустой последний assistant с tool_calls не заменяется старым ответом.
3. Единственный текстовый лист после исключения протокольных метаданных.
   Несколько равноправных листьев или историй остаются неоднозначностью.

Конверт имеет приоритет над соседним внутренним состоянием, сообщения с
ролями — над их неразмеченными копиями. Эти правила зависят от структуры,
а не от значения текста. Числа в строках, URL, короткие ответы, точное
повторение вопроса и внутренние переводы строк сохраняются. Текст внутри
явной реплики не разбирается повторно как JSON. Вызовы инструментов,
`additional_kwargs`, `response_metadata` и другие служебные поля исключаются.

**Синхронный ответ.** Входящий FIPA request и обычное выходное тело одного
граничного спана образуют синхронную пару. Наличие FIPA на входе само по себе
не требует асинхронного соединения. Входящий inform и подтверждение его
приёма не образуют пользовательскую пару.

**Асинхронный FIPA.** Вход `request` и конечный `inform`, `failure`, `refuse`
или `not-understood` соединяются по `(conversation_id, reply_with/in_reply_to)`.
Исходящий `request` — передача задачи, `agree` — промежуточное подтверждение.
Отсутствующий перформатив не считается конечным ответом.

Участник считается инициатором conversation, если прислал request раньше,
чем агент отправил request ему. Если во входных данных есть свидетельство обратной
роли участника, обрезанное начало другого conversation не используется для
автоматической смены роли. При равном времени порядок определяется только
для входа и выхода одного спана. Самообращения исключаются. Собственный conversation
исходящего сообщения сохраняется; при его отсутствии используется conversation
входящего конверта того же спана. Произвольное обрезанное окно не всегда
позволяет установить внешнюю сторону — такой обмен остаётся в диагностике.

Проверяются совпадение участников, сессий, порядок времени и непротиворечивость
реплик одного ключа. Сравнение текстов точное, без приведения регистра или
схлопывания внутренних пробелов. Разделители в компонентах `turn_id` экранируются.

`route_label` — получатель наблюдаемого исходящего request. Первый текстовый
фрагмент, короткое слово или имя внутреннего узла не объявляются маршрутом.
При отсутствии маршрута поле остаётся пустым. Для accuracy это может означать
отсутствующий prediction; конвертер не восстанавливает класс по смыслу ответа.

## UMR и готовность

Для `qa` и `turn_with_history` строка содержит `scenario`, `session_id`,
`query_id`, `input_query_count`, `input_query`, `output_answer`.
Для `dialogue` одна строка сессии содержит список троек
`(query_id, input_query, output_answer)` в `dialogue`. Дополнительные поля
prediction и `solution_version` публикуются по существующему контракту.
Эталоны и оценки ассессоров из трейсов не выдумываются.

DataFrame и parquet содержат полный текст. XLSX сохраняет ту же структуру,
записывает ведущий `=` как текст, заменяет запрещённые управляющие символы и
помечает обрезку ячеек длиннее 32 767 символов. Обрезки перечислены в отчёте.

- `complete`: все обнаруженные обращения извлечены, нет потерь исходных
  спанов/трейсов, необходимые источники scoring доступны.
- `partial`: источники scoring доступны, но есть пропуски, конфликты или traces
  без границ. Публикуются полные пары. `ready_for_scoring=False`, `data_readiness.state=limited`.
- `not_ready`: нет полных пар, не хватает источников scoring, входная метрика
  `not_computable` или не пройден DQ-гейт. При нуле пар возвращаются пустые
  UMR/parquet/XLSX с диагностикой. Нарушение структуры входа вызывает
  `TraceExtractionError` или ошибку валидации контракта.

Вложенный отчёт извлечения имеет версию `laim-trace-turn-extraction.v3`:
он описывает границы, происхождение текста и полноту извлечения. Поля
внутреннего состояния вне внешнего спана не подтверждают доставку ответа
пользователю.

## Диагностика

`issues.counts` содержит полные счётчики, `issues.examples` — не более 100
примеров с ID и причиной, без тел сообщений. При обрезке примеров выставляется
`examples_truncated`. Диагностика сохраняется и при пустой UMR.
`extraction.discovery` показывает пути неоднозначных текстовых кандидатов.

Учёт строк проверяется двумя равенствами:

```text
selected_agent_rows = duplicate_span_rows + conflicting_span_rows
                    + invalid_span_rows + non_candidate_rows + candidate_rows_scanned
candidate_rows_scanned = inner_boundary_rows + fipa_rows + aef_candidate_boundaries
                       + ambiguous_envelope_rows + blocked_boundary_rows
```

`candidate_turn_keys` считает ключи FIPA, синхронные границы и неразрешённые
граничные события. `complete_turns / candidate_turn_keys` — покрытие этих
кандидатов. Это не доля всех реальных диалогов: во входных данных могут отсутствовать
целые границы. Поэтому отдельно считаются `no_boundary_trace_count`, отброшенные
строки и конфликты; даже покрытие 1.0 не отменяет эти ограничения.
`conservation.published_turns` отличается от `published_rows` для packed dialogue.

| Причина | Что проверить |
|---|---|
| `boundary_pair_incomplete` | `details` и пути в `discovery`: отсутствует текст, время или есть неоднозначность |
| `entry_without_exit`, `exit_without_entry` | Границы временного окна и ключи conversation/request |
| `conflicting_*_replicas` | Разные тексты, маршруты, сессии или участники одного ключа |
| `envelopes_ambiguous`, `ancestor_*`, `parent_cycle` | Конверты и связи родителей |
| `start_agent_not_root` | Внутренний запуск без наблюдаемой внешней границы |
| `forwarded`, `fipa_boundary_unresolved` | Есть ли конечный ответ внешней стороне |
| `no_boundary_span` | Присутствуют ли внешние спаны во входной таблице; chain/llm сами по себе недостаточны |

Тела сообщений без обязательных колонок спана не принимаются.
Контекстные ID не подставляются вместо `trace_id`, `span_id` и `session_id`.

## Теневой LLM-анализ

Настройки доступны в UI; новые входные порты не требуются.

| Настройка | По умолчанию | Допустимые значения |
|---|---|---|
| `llm_mode` | `off` | `off` — без вызовов; `shadow` — предложения в отчёте |
| `model_id` | пусто | Модель шлюза; пустое значение использует `LAIM_LLM_MODEL`, затем `glm-5.2` |
| `llm_max_calls` | `6` | Целое число от 1 до 6, включая неуспешные попытки |
| `llm_budget_seconds` | `180` | Целое число от 1 до 180; общий лимит LLM-этапа |

Подключение задаётся переменными окружения контейнера: `LAIM_LLM_URL` и
`AI_GATEWAY_API_KEY`. Адрес по умолчанию —
`http://sds-ai-gateway:8097/api/v1/chat/completions`. Для этого адреса при
отсутствии ключа используется принятое шлюзом значение `123`; другой адрес
требует явного ключа. Ключ не передаётся через порты и не включается в отчёт.
Шлюз должен поддерживать chat completions с `messages`, `max_tokens` и
ответом `choices[].message.content`; SDK конкретного провайдера не требуется.

Помощник рассматривает неоднозначный выбор текстовых полей только внутри
подтверждённой пары вопрос/ответ. Для FIPA нужны ровно один вход и один
конечный выход одного ключа, совпадающие непустые сессии и корректное время.
Реплики, неполные события, неизвестные границы и неполностью распознанные
структуры исключаются. Модель не дополняет отсутствующий текст, не определяет
маршрут и не пересматривает уже однозначно извлечённое поле.
Ответы с объявленным `status` / `status_code` равным `error`, `failed` или
`failure` также исключаются: поля диагностики ошибки не становятся ответом.

Кандидаты группируются по структуре, типам, роли проекции и протоколу.
Рассматриваются три наиболее частые допустимые структуры. Для каждой
выбираются до шести примеров по устойчивому хешу исходной идентичности;
порядок строк не влияет на выбор. Два запроса получают непересекающиеся
группы примеров и независимо выбирают ID исходных полей либо отказываются.
Для структуры с единственным примером вызовов нет. Если оставшегося бюджета
не хватает на два запроса, структура пропускается.

Нормализованный путь должен обозначать ровно одного кандидата в каждом
примере. Модель не возвращает исполняемые пути или новый текст. Одинаковый
выбор в двух запросах получает статус `agreed`; это согласованность выбора,
а не подтверждение его смысловой правильности.

Бюджет ограничивает ожидание помощника внутри функции ноды. Отменённый
системный DNS-запрос может завершаться в фоне; время остановки самого
Python-процесса зависит от resolver ОС и не входит в эту гарантию.

Один запрос ограничен 60 секундами в пределах общего бюджета. Повторных
попыток и запросов на исправление ответа нет. Максимум — 32 кандидата на
сторону, 16 КиБ сериализованных полей примера, 96 КиБ контекста запроса,
16 384 токена генерации и 128 КиБ HTTP-ответа. Структуры глубже 32 уровней
или больше 2048 элементов исключаются. Превышение лимита исключает пример
целиком: обрезанный текст не используется для выбора. Сбор хранит до шести
примеров на структуру; постоянного реестра и обучения между запусками нет.

`processing_report.llm_assistance` имеет контракт
`laim-trace-llm-assistance.v1`. Он содержит настройки, хеш промпта, счётчики,
время, число попыток и доступную статистику токенов по каждой попытке
(`null`, если шлюз её не сообщил). `families` содержит результаты анализа,
хеш правила, выбранные пути и до шести ссылок на исходные события.
`applicable_pairs` считает структурно подходящие пары для предложения;
это не число дополнительно опубликованных turns.

| Результат | Значение |
|---|---|
| `disabled`, `skipped` | Анализ выключен либо отсутствуют допустимые данные |
| `agreed`, `disagreed`, `abstained` | Совпадение выборов, расхождение или отказ модели |
| `insufficient_examples` | Нет двух независимых примеров структуры |
| `call_budget_exhausted`, `time_budget_exhausted` | Исчерпан лимит вызовов или времени |
| `invalid_selection`, `invalid_json`, `incomplete_response` | Ответ не прошёл локальную проверку |
| `http_*`, `transport_error`, `request_timeout` | Ошибка шлюза или соединения |
| `gateway_configuration`, `gateway_credentials` | Некорректная настройка подключения |

Тела сообщений, промпты и ответы LLM не записываются в отчёт или логи.
При ошибке помощника основной результат сохраняется, причина остаётся в
теневом отчёте. При красном DQ или `monitoring_metric.status=not_computable`
LLM не вызывается. При нуле извлечённых turns анализ допустимых кандидатов
выполняется, но UMR остаётся пустой с исходным `not_ready`.

Для оценки пилота в контуре нужно независимо разметить правильность
предложенных пар, включая вопрос и конечный ответ. Сравниваются точность,
подтверждённый прирост, отказы, задержка и расход токенов; часть структур
должна оставаться вне настройки промпта. Согласие модели с собой не заменяет
разметку. Автоматическое применение предложений в этой версии отсутствует.

## Код, проверка и сборка

- `table_io.py`: чтение таблицы.
- `bodies.py`: разбор и проекция тела.
- `fipa.py`: участники, события и соединение FIPA.
- `trace_dialogue.py`: границы, идентичность, учёт строк и provenance.
- `canonical.py`: проекция turn в UMR.
- `shadow_extraction.py`: кандидаты, выбор примеров и теневой отчёт.
- `llm_client.py`: подключение к шлюзу, лимиты и проверка ответа.
- `main.py`: порты, гейты, сериализация и отчёт.

Python 3.12, зависимости из `requirements.txt`.
Проверки из корня ноды:

```bash
python -m pytest -q
ruff check .
```

CI использует `ruff==0.15.5`. Проверки охватывают синхронный и асинхронный
обмен, смешанный FIPA/JSON, обёртки и массивы, роли сообщений, multipart,
инструменты, несколько обращений в trace, конфликты, циклы, legacy-колонки,
перестановку строк, неполные окна, QA/history/dialogue и сериализацию.

В сборку входят `descriptor.json`, `requirements.txt`, `README.md` и все
файлов из `script.runConfiguration.sourceFiles`. Точка входа — `main.main`,
базовый образ — `py312-simple`.
